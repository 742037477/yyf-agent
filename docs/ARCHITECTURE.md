# 架构对应与分阶段计划

封版说明：2026-10-31 已封版，定位、边界与实验结论见 [POSITIONING](POSITIONING.md)。
下文分阶段计划中未完成的部分全部冻结；正文保留作历史设计参考。

目标架构：M2 通用 Agent 全局架构 v1.1、动态子 Agent / WP 任务链路 v1.1（原项目 `docs/architecture/20261005-two-level-r2/`）。
本内核按“每阶段都能端到端跑通真实任务”的方式逐步实现该架构。

## 目标

核心：任何人把 Agent 放进框架执行各种任务，框架都能阻止或揭露 Agent 的**撒谎**（声称完成但未完成）、
**欺骗**（篡改验收、伪造记录、误导审查）和**窃权**（越出授权的读写、联网、取密钥、扩权转派）。
配套：动态子 Agent 执行链路（分配、召回、改派接手、继承与指派）、框架授信与自我保护。

定位：大厂与开源方案（如微软 Agent Governance Toolkit）已在做“管动作”（策略拦截、身份、沙箱、审计日志）；
本框架的重点是“管结论”——Agent 无法谎称完成：独立验收与跨厂商独立审查绑定同一冻结候选、三态判定、只交付验证过的版本、
UNKNOWN 先对账不重放、接手以账本事实为准。
定位确认（2026-10-14，用户）：M2 是架在各家 Agent（Codex、Claude Code、DeepSeek Harness、ZCode、WorkBuddy 等）之上的
**中立治理与公证层**。只做厂商结构上不会做的三件事：权威握在用户的离线 Root 手里；验收由任务方提供、审查跨厂商独立；
交付附带第三方可核验的证据链。沙箱、审批、运行日志这类运行环境安全，能用厂商自带的就用，不重复造。

第二个核心（2026-10-13，用户）：**最高 Root 私钥离线隔离**。Root 私钥只在 Agent 永远触达不到的离线环境中使用，
用它签发对框架自身的授权（框架授权书）；框架再在授权范围内给进入框架的 Agent 分发权限；Gate 只持有 Root 公钥、只做逐级验签。
因此运行环境被攻破也铸造不出权限，Agent 无法窃取最高权限或改写授权。成立条件：私钥物理隔离；
运行时只有公钥；框架代码与锚定公钥对 Agent 不可写（隔离执行 + Root 签名的发行清单 + 外部核对）；
每个授权签名绑定任务、范围、有效期与撤销状态，Gate 在每个动作前重新验签。

签发环境（用户，2026-10-13）：正式 Root 私钥存于 U 盘，签发路径固定为 H 盘，只在断网且无任何 Agent 进程时插入签发。G 盘下的密钥仅为测试用途；框架须区分 TEST_ONLY 与正式信任域，正式配置下拒绝测试 Root 签出的任何授权。决定（用户，2026-10-13）：签名与验签机制**前置**——第 2 阶段就用测试 Root 完整实现并持续接受攻击场景检验，只有正式 Root 的离线签发仪式后置。开发与测试全程沿用已有的测试 Root（TEST_ONLY），正式 Root 的离线签发推迟到制作正式发行包时进行；代码必须做到切换信任根只改配置（锚定的 Root 公钥与信任域标记），不改代码。测试根用法（用户决定）：自动测试与 CI 用每次临时生成的密钥；端到端演练沿用旧项目的测试根（TEST_ONLY，位置在第 2 阶段开工时确认，候选为 <offline-keys> 或旧仓库 control/trust），开工时先只核对其公钥格式是否为 Ed25519；测试根私钥不进入 m2-kernel 仓库，也不上传 CI。签发前采用“轻量检查”（用户决定）：断网、关闭全部 Agent 与相关进程、核对计划任务与启动项无陌生程序后再插 U 盘；第 2 阶段提供只读的签发前自检脚本辅助核对。

决定（2026-10-13，用户）：全部能力原生实现，不接入外部治理组件；可参考其设计与公开标准（OWASP Agentic Top 10、DID 等）。唯一允许的依赖是通用密码学库 `cryptography`，用于 Ed25519 签名与验签。

每个阶段的验收都包含“攻击场景”：一个故意作恶的 Agent 被拦下或被揭露，写进 `m2k accept`。

## 分阶段

| 阶段 | 内容 | 完成标准（含攻击场景） |
| --- | --- | --- |
| 1 ✅ 骨架 | 单任务全链、账本、G3/G4/G6/G7、三态、预算、受保护文件 | 真实模型场景验收 10/10（2026-10-13）；声称完成但验收不过 → FAIL |
| 1.5 ✅ 防窃权与防欺骗加固 | 命令执行清除密钥环境变量（T04）；审查防注入（T05）；验收必须由任务方提供（T06）；本地账本移出工作区（T07）；命令在隔离环境执行（限定目录、默认断网，T08）；账本链头外部锚定（T09）；字节码劫持（T10）；模型断线记 UNKNOWN（T11）；改账本攻击演练（T12）；审查流式回复（T13） | 读密钥、读工作区外文件、联网外传、改写或重算账本、在文件里指挥审查者、自己写验收或用同名模块劫持验收 → 全部失败或被发现（2026-10-13 完成，离线场景 16/16） |
| 2 ✅ 离线 Root 与签名授权 | Ed25519（`cryptography` 库）。信任链：**Root（离线）签发框架授权书** → **框架给进入框架的 Agent 分发权限** → **Gate 逐级验签**。框架授权书 = 框架发行清单指纹 + 框架签发公钥 + 框架可授出的权限上限（动作、路径、预算）；**授权书永久有效，只要不更换 Root**（用户决定 2026-10-13），失效途径只有 Root 离线签发的撤销单或更换 Root；任务凭证仍按任务限期；框架签发私钥只在框架受保护进程内（Agent 的隔离环境之外）；框架签给 Agent 的准入与任务凭证不能超出 Root 授给框架的上限；Gate 只持 Root 公钥，每个动作前验“Agent 凭证 ← 框架签发公钥 ← Root 签名”整条链（G0/G1/G2）；撤销与过期 | 伪造、过期、已撤销、挪用到别的任务的凭证被拒；测试 Root 签出的授权在正式配置下被拒；框架授出超过 Root 上限的权限被拒；替换锚定公钥或框架授权书被发现；Agent 的隔离环境内找不到任何私钥 |
| 3 ✅ 动态子 Agent | 父任务的 GLOBAL/DECISION 形成任务图，按需拆出子任务并形成执行链路，每个子任务自带 EXECUTION/TEST/AUDIT；子凭证由签名委派产生，权限与预算只能收窄，预算原子预留；**召回**：中止子 Agent 并撤销其凭证，旧 epoch 迟到结果保留但不覆盖；**改派接手**：新子 Agent 接手，历史经验取自账本事实而非前任自述，前任 UNKNOWN 先对账，预算累计不重置；有界修复；作者不能自审；全局组合验证 | 子凭证扩权被拒；召回后动作被拒；并发抢额度只成功一个；接手者不重复已证失败做法；组合任务 PASS（2026-10-15 完成：T21–T29；攻击演练 20/20 被拒或被发现，离线场景 23/23；T29 真模型端到端：规划模型首次方案即通过，3 个子任务各自审查、合并，总验收 PASS） |
| 3.5 需求变更 | 需求、计划、验收版本化；变更只让受影响的子任务、候选与审查失效，未受影响证据复用；范围外变更先保持、待授权 | 改验收版本后旧候选失效，无关子任务结果保留 |
| 4 中断与续接 | 进程级检查点；中断后从账本恢复；UNKNOWN 效果先对账，绝不重放 | 强杀进程，`m2k resume` 后完成且无重复效果 |
| 5 框架自我保护 | 启动时按 Root 签名的发行清单自检代码与配置；账本链头签名；Agent 不能修改框架、配置或自身权限；独立 OBS；只读裁决 | 篡改框架或配置 → 拒绝运行并记录；OBS 中断或被篡改可检测 |
| 6 记忆与经验库 | 跨任务记忆与经验，带来源/版本/适用条件；召回不授予权限；采纳闭环 | 同类失败任务第二次召回经验并减少轮数 |
| 7 适配器（首个提前到 3 之后） | 通用 CLI Worker（Python 调各家非交互命令行）：Codex、Claude Code、DeepSeek Harness，ZCode 经其底层 CLI（WorkBuddy 已排除，2026-10-17）；结论级治理全覆盖，有钩子的加动作级；声明能力与未验证项 | Codex 作为 Worker 在治理下完成同一编程任务（首个适配器 7a ✅ 2026-10-15：T37，用户 Windows + ChatGPT 登录真跑 codex-demo-7 PASS，GLM 跨厂商审查 GO） |
| 8 交付给他人 | 安装包、使用手册、模板、攻击场景演示；人工接受状态；真实混合长任务 | 他人在另一台电脑复现全部攻击场景；长任务结果经用户人工接受 |

信任链默认必需（2026-10-14，用户）：没有 `[trust]` 时 `m2k run` 拒绝启动；只有所有者逐次加 `--untrusted` 才能不授权运行，账本记 `trust: null`，报告标红；`m2k trust init-dev` 一步生成 TEST_ONLY 测试链。内核本身仍允许 `trust=None`（测试与离线场景用），规则落在启动任务的入口（T20）。

第 3 阶段决定（2026-10-14，用户）：
- 子任务的验收只能从任务方提供的验收文件里选；规划模型写的测试不能当子任务验收（不自己出题自己判卷）。
- 第 3 阶段子任务一个接一个执行；预算预留仍按并发标准实现并用并发测试证明，真正并行留到适配器之后。
- 模型拆出的方案过 Gate（范围在父任务内、预算总和不超、验收来源合规）后自动执行并全程记账，不停下等确认（暂停续接属于第 4 阶段）。
- 拆卡：T21 任务树骨架 → T22 子凭证委派 → T23 预算原子预留 → T24 召回与改派（T25 有界修复、T26 强制作者不自审可并行）→ T27 模型拆任务 → T28 攻击演练 → T29 端到端实战。

第 5 阶段决定（2026-10-15，用户）：
- 三个角色分开。内核干活、记账；**只读裁决器**只读账本和旁证，自己从头重算结论，只给出核验结果，不发布任何东西；**Gate** 是唯一能发布的环节，只认裁决器的核验结论和公证回执，不认内核自己报的 PASS。
- **OBS（独立旁证）先全部放在本地**，做成独立进程，有自己的密钥、自己的哈希链，链头锚定到外部。设计上不绑定位置：以后可以换成另一个系统用户、单独的机器或云端，回执格式和 Gate 的校验都不用改。回执里写明公证方和强度（本地 / 云端）。
- 本地 OBS 防不住的情况要如实写明：Agent 和 OBS 是同一个系统用户、又没有隔离时，专门针对框架的攻击能读到 OBS 的密钥。需要更强保证时，再加云端公证方；GitHub Actions 是最低成本的选择。
- 安全不靠“文件出现在交付目录里”，而靠“有没有一张有效回执”：没有回执、或者回执和文件对不上的产出，一律视为未经核验。
- 第 5 阶段以攻击演练收尾：Agent 攻击框架本身（改框架代码、改配置换审查者、替换 Root 公钥或授权书、绕过 Gate 直接放文件、伪造回执、内核记 PASS 但事实不支持），每一种都必须被拦下或被发现。
- 整套替换 Root（2026-10-17，用户，T46 演练发现 a21）：本机同用户模式下，Agent 能用自建 Root 重签授权书、清单、配置和吊销单，连同 OBS 密钥、锚点仓库一起换掉；除了离线 Root 私钥，框架没有别的东西能证明“这是所有者的 Root”。全套替换只能靠硬隔离解决。决定（2026-10-17，用户）：先做**本机独立用户隔离**——框架代码、配置、Root 公钥、OBS、账本和模型 API Key 放在独立 Windows 用户（如 `m2k-svc`）名下，Agent 以受限普通用户运行、只能写工作区，不经框架就调不了模型；这是单道防线（离线 Root 私钥 + 系统用户权限），Agent 不能用管理员账号运行。**独立隔离 OBS**（另一系统用户或另一台机器）原定作为第二道防线，2026-10-17 用户决定暂不考虑、排除出路线图。先做小卡 T65：OBS 记住每个信任域首次见到的 Root，换 Root 即拒绝启动（`ROOT_CHANGED`）；远端核对发现公证方与已发布锚点不一致即报出；每次运行和 `trust status` 醒目显示 Root 指纹。
- 本机独立用户隔离的落地方式（2026-10-17，用户）：两个 Windows **标准用户**——`m2k-svc` 拥有框架代码、配置、Root 公钥、OBS 密钥与日志、账本、模型 API Key；`m2k-agent` 运行被治理的 Agent（Codex、Claude Code、dsh），只能写本次任务的工作区。**按需启动**：用户照常 `m2k run`，任务放进队列目录，由一个以 `m2k-svc` 运行的计划任务执行，跑完即退出（不做常驻服务）；`m2k-svc` 以 `m2k-agent` 身份启动 Agent（标准库 ctypes，`m2k-agent` 的密码经 DPAPI 加密、只有 `m2k-svc` 能解）。Agent CLI 需在 `m2k-agent` 账号里各自登录一次；它们直连自家模型是正常的，但拿不到 M2 的模型 Key。启动时自检文件权限（`m2k-agent` 读不到密钥、改不了框架和配置），PRODUCTION 下不过即拒绝启动。**接受并写明的局限**：管理员账号可无视文件权限，用户在自己的管理员账号下亲自使用的工具视为可信、不在治理范围内；第 8 阶段发行时再建议日常使用标准账号。拆卡：**2 张**——① 安装脚本（建用户、设权限）+ 启动自检 + 以 `m2k-agent` 启动 Agent（Codex 实现）；② 真机攻击演练（Agent 试图读密钥、改配置、换 Root、用 M2 的 Key 调模型），在用户电脑上跑。顺序：**先隔离，再第 3.5 阶段**。
- 隔离线暂停与验证范围（2026-10-27、2026-10-28，用户）：本机账号 ACL 隔离（T77）暂停，已装的 T76 留现状不拆，WSL/容器暂不做；现阶段对 Agent 只靠“事后发现”（T73 补上工作区实时观测与工作区外监视路径）。由此**如实写明验证范围**：
  - **本机（Windows，同一用户、无隔离）只验证“防跑偏的可信 Agent”**：被注入或跑飞的厂商 Agent 谎称完成、改验收、改框架或配置、改账本与回执，会被拒绝或被发现。**不验证“防专门攻击框架的 Agent”**：同用户下 Agent 读得到 OBS 私钥、TEST_ONLY 开发 Root 私钥和所有者的 git 凭据，能重签配置与清单、伪造回执，在下一次运行前抹平痕迹。
  - **“防专门攻击框架”的验证放在有系统层隔离的环境里做**：GitHub 的 Linux 跑机（命令以无 sudo 的 `m2kw` 用户执行、密钥只在 root 专属文件里，见 T04），T46 演练即在此环境通过。
  - 本机要达到同等保证，前提是隔离恢复（第 8 阶段交付给他人或运行不可信 Agent 之前，先做 T77 威胁模型调查再选隔离原语）。
- 隔离之后由框架自签（2026-10-28，用户）：Root 私钥只做很少的事——签框架授权书、吊销授权书、批准超出上限的变更；日常由框架签发私钥（只在 `m2k-svc` 名下，Agent 读不到）在授权书上限内签：任务凭证（T16 起已如此）**以及配置变更与发行清单**，不再每次插 U 盘。原则：**收紧可自签，放宽要 Root**。“上限”有两层：
  - **工具与联网上限**：授权书 `caps` 里的工具清单、是否联网。框架签出的任何东西都不能超过；要放开就由 Root 签新的授权书。
  - **预算不归 Root 管**（2026-10-28，用户）：四项预算（`max_rounds`、`max_model_calls`、`max_tokens`、`max_commands`）是花费控制，不是权限。超出现有预算上限时不需要 Root，保持框架的灵活性；两条路都要所有者本人拍板、框架再签发（记账 `budget.raised`，带 OBS 回执）：
    ① **请求—核验**：任务跑到预算上限（或 Agent 申请追加）时挂起待授权，所有者人工核验后确认，框架签发追加额度、任务以新版本接着做（挂起与授权见 T49，续做见 T48）；
    ② **所有者自主授权**：所有者不等请求，自己主动调整某个任务（或之后任务）的预算，框架核对后签发；**也包括所有者事先定义的规则**（如“每个任务可自动追加不超过 20%，超过才问我”）。规则本身只能由所有者经同一所有者通道定义或修改（Agent 不能），框架按规则自动签发的每次追加都记账，写明依据哪条规则、追加多少；规则之外的追加回到 ①。
    “所有者本人”的证明：隔离后靠只有所有者能写的 inbox；隔离前（T49）靠专用的 `m2k answer` 类命令记账。代价（已接受）：框架签发私钥若泄露，花费不再有 Root 级的上限；工具、联网、信任根仍由 Root 框住。实现时授权书的 `caps` 去掉四项预算，Gate 改为核对框架签发、所有者批准的预算记录。
  - **配置基线**：最近一份 **Root 签的**发行清单所对应的配置。框架只能签“与基线相同或更严”的配置——可以加监视路径、加保护目录、调小预算与超时、换 Agent 程序路径；不能改 `[trust]`、`[obs]`、`[anchor]`（Root、OBS 密钥、锚点、公证方），不能打开 `allow_same_model` 或让审查者与执行者同厂商，不能删监视路径，不能把隔离后端降级（如 `bwrap` → `none`）。这些属于放宽，必须 Root 签。
  - 所有者意图的证明靠隔离：所有者用 `m2k config propose` 把改动投进只有所有者能写的 `queue\inbox\`；以 `m2k-svc` 运行的框架比对基线，收紧则签新版本清单并记账 `config.changed`（带 OBS 回执，版本号照常 +1，T64 防回滚不变），放宽则拒绝并提示要 Root。
  - 前提：隔离必须保护框架签发私钥，并且只让所有者能往 inbox 投递；隔离暂停期间不实现。框架签发私钥泄露的损失被授权书上限和 Root 基线框住；Root 一直离线。

第 3.5 阶段决定（2026-10-28，用户）：
- 改需求只在两次运行之间发生：所有者用 `m2k run --amends` 开契约新版本，从旧版本最后冻结的候选接着做；预算是所有版本的总额（T48）。
- 影响分析（T49）：只复用所有者亲手写的子任务；按顺序，前面有子任务重跑则后面全部重跑；子任务本身、父任务目标/约束/受保护文件、子任务验收文件、
  写入范围内的文件、以及除“该子任务不用的父任务验收文件”之外的任何所有者文件有变化，都重跑。父任务的验收与终审总是重跑。
- 挂起与所有者批准（T79）：Agent 用 `ask_owner` 提问或申请扩大范围/追加预算，任务以“待授权”结束（UNKNOWN，退出码 3）；顶层任务预算用完同样改为“待授权”
  （子任务照旧）。隔离前“所有者本人”的证明：专用命令 `m2k answer` 只能在交互终端运行、所有者亲手输入 YES；在 `--amends` 里扩大范围、加工具、联网、
  加预算都必须经过它。挡得住跑偏的 Agent，挡不住专门攻击（与本机验证范围一致）。
- 自动预算规则（T80）：只能由所有者用 `m2k owner-rule`（交互终端 + YES）定义或撤销，记在账本；同一任务所有版本累计，每项自动追加总量
  ≤ 第一版预算 × 规则百分比；只在预算用完挂起时触发，框架自动开下一版并记 `budget.raised`（写明规则）；超出部分回到请求—核验。隔离前追加后仍不得超过授权书 caps。

- 授权两种模式（2026-10-28，用户补充；取代上面 T80 只管预算的写法）：
  - **预授权（发起提问前放权）**：所有者事先在契约里（或用 `m2k owner-rule`，交互终端 + YES）写“可放行范围”——可额外写的路径、可加的工具、
    能否联网、预算最多追加多少。Agent 用 `ask_owner` 申请的东西落在范围内时，框架当场放行、任务不停，记账写明依据哪一条（带 OBS 回执）；
    超出范围才走实时授权。预授权和放行后的结果仍不得超过授权书 caps（Root 框住）。（T80）
  - **实时授权（提问后停下来等）**：运行不结束，原地挂起等所有者（等待时长可配置，如 30 分钟）；所有者在另一个终端用 `m2k answer`（交互终端 + YES）
    批准后，同一次运行接着做（原生 Worker 保留对话），框架在 caps 内重签凭证并记账；超时无人回答才以“待授权”结束，之后用新版本续做（T79 的做法）。（T81）
  - 运行中只能**放权**（范围、工具、联网、预算）；改需求（目标、验收）仍只在两次运行之间开新版本（T48）。裁决器核对每一次运行中放权都有依据（预授权条款或所有者批准）。
  - T79（Agent 提问、挂起待授权、`m2k answer`、批准核对）是两种模式共用的底座，照常做完。

重构方向决定（2026-10-29，用户）：T82 价值对照实验（单任务、顶级模型）显示 m2k 比“干完自己跑验收”多拦下 0 次、额外耗时中位约 2.2 倍；
用户确认转向“规模化、便宜模型、可核验”：用便宜模型大规模并行做大任务，靠分层验证让错误不随子任务数叠加，结果可核验。
- 治理放在边界：工作区内部只记账；交接与合并做机械验收（可见 + 隐藏双验收），AI 审查按风险抽样、失败自动重审；
  资源与权限走 Gate + 预授权（T80）/ 所有者批准（T79）；不可逆与对外操作强审查或人批准；事后靠账本与裁决器。
- 内核改为账本驱动的节点状态机（状态不放进程内存），在其上加调度器（并行、写入租约、限流）、合并队列（主干测试）、
  上下文组装（目标链与契约原文钉住、事实带出处）、多层规划/整合 Agent。
- 迁移顺序：R0 规模化基准（N = 10/30/100，先用现有内核跑基线，判定标准事先写死）→ R1 只重构不改行为 → R2 节点契约
  → R3 调度器 → R4 合并队列与分层验证 → R5 续跑 → R6 上下文与多层编排。
- 冻结：T81 实时等待授权、本机隔离（T77 起）、第 6 阶段经验库。

顺序决定（2026-10-14，用户）：第 3 阶段之后先做第一个适配器（阶段 7 的最小版本），尽早证明 M2 能治理别人家的 Agent；之后再做 3.5、4、5、6 和其余适配器。
