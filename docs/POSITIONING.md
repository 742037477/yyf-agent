# m2k 的定位、边界与实验结论

## 1. 一句话

m2k 是给 AI Agent 产出用的“审计与可核验层”：交付前跑所有者的验收和独立审查，
只交付判 PASS 的那一份冻结候选；全程写进只追加、哈希链接、有旁证回执和外部锚点的账本；
交付之后任何人可用回执核验文件有没有被改。

这里的 PASS 只表示该候选通过了当时的验收、审查与裁决。
它的含义受验收内容、信任配置和运行环境约束，不能替代所有者对需求和风险的判断。

## 2. 管什么

| 要核对的事 | 机制 | 命令或任务卡 |
| --- | --- | --- |
| 只交付 PASS 的冻结候选。 | 验收、独立审查和只读裁决绑定同一摘要，G6 放行后由 G7 核对落地文件。 | `m2k run`；[T39](../tasks/T39-read-only-adjudicator.md)、[T47](../tasks/T47-delivery-receipt.md) |
| 验收文件受保护，改了判 FAIL。 | 验收由所有者提供，工具写入受限，验收前再核对保护文件的哈希。 | [T06](../tasks/T06-owner-acceptance.md) |
| 事后改写账本可被发现。 | 只追加账本的哈希链配合 OBS 签名回执和外部锚点，核对已见过的历史。 | `m2k check-ledger`、`m2k check-ledger --remote`；[T42](../tasks/T42-obs-witness.md)、[T63](../tasks/T63-external-anchor.md) |
| 结论可以从账本重算。 | 只读裁决器不接受内核自报的 PASS，按事件和候选摘要重建判定。 | `m2k adjudicate <任务 ID>`；[T39](../tasks/T39-read-only-adjudicator.md) |
| 交付后可以核验文件与回执。 | 便携回执绑定交付事件、文件哈希与 OBS 签名；没有有效回执的产出标为未经核验。 | `m2k check-delivery <目录>`；[T47](../tasks/T47-delivery-receipt.md) |
| 授权、凭证、预算与写入范围要符合约定。 | Gate 检查签名信任链、任务凭证、额度及路径；预算用量从账本事件推导。 | [T14](../tasks/T14-trust-core.md)、[T16](../tasks/T16-trust-in-kernel.md)、[T23](../tasks/T23-budget-reservation.md) |
| 改需求要开新版本，扩权要有所有者批准或预授权。 | 旧结论失效，新版本重新验收审查；批准和自动放行均入账，裁决器重放核对。 | `m2k run --amends`、`m2k answer`；[T48](../tasks/T48-contract-versions.md)、[T79](../tasks/T79-owner-requests.md)、[T80](../tasks/T80-preauthorization.md) |
| 指定的工作区外配置被改时可以发现。 | `[watch]` 比较所有者指定路径的内容，变化记账并判 FAIL，无法完整核验则 UNKNOWN。 | [T73](../tasks/T73-workspace-watch.md) |

模型回复只是提案；只有 Worker 在 Gate 允许后调用工具，才会产生效果。
每次效果前后都有同一操作标识的意图与结果记录；审查者看不到 Worker 的对话。
FAIL 表示已证实失败，UNKNOWN 表示无法判定；两者都不交付。
缺失的用量保持未知，不按零计算。

## 3. 不管什么 / 证明不了

**不让可信厂商 Agent 做得更好。**
[T82](../tasks/T82-value-experiment.md) 中，顶级 Agent 本来就不谎报、不改验收、不理注入；
m2k 多拦下 0 次，耗时多一倍以上。这是本次实验的结论，不能外推到所有 Agent 和任务。

**不能靠“便宜模型 + 验证”规模化追上贵模型。**
[T84](../tasks/T84-r0-scale-benchmark-run.md)、[T85](../tasks/T85-r0-decisive-experiment.md)
都未通过事先写定的规模化判定规则，因此不继续这条路线。

**AI 审查的增益在这些实验里没有得到支持。**
T84 中 GLM 71 次 GO、1 次 NO_GO，且那 1 次可见测试已经挂了；
审查几乎没多拦下东西，却是最贵的环节。独立调用不等于判断一定可靠。

**验收写得对不对由所有者负责。**
m2k 只照验收判；验收漏掉需求，或者断言本身写错，回执不会补全需求，也不会纠正断言。
回执证明“这份文件就是当时验收和审查通过的那份”，不证明验收本身写得对。

**本机同一 Windows 用户运行，没有系统级隔离。**
专门攻击框架的 Agent 可能伪造批准、拿到 OBS 私钥；拿得到私钥的人可以签假回执。
正式使用时，OBS 私钥应只在框架服务账号下，Agent 不应能读取或改写框架私有状态。
这项部署前提没有由当前同用户演示实现，账号隔离（T75～T77）已暂停。
读取机密并外传看不见，`[watch]` 只揭示指定路径的改动，不阻止改动。

Linux 上命令在 bubblewrap 里跑；
[T46 攻击演练](../tasks/T46-stage5-attack-drill.md) 在 GitHub 的隔离 Linux 环境通过。
这个结果只覆盖该环境及演练场景，不能当作本机 Windows 同用户环境的隔离证明。

**尚未测到的场景：**任务之间互相依赖、长时间无人看管、不可信 Agent、
不可逆动作（发布、删除、付款）。现有实验不足以说明这些情况下的表现。

## 4. 什么时候值得用

日常用可信厂商 Agent，跑完自己跑测试、留下记录就够了。
现有实验没有显示再套一层 m2k 会让这类单任务完成得更好。

需要向别人证明“这份交付经过了验收、交付后没被改过”，
或者要事后追查谁在什么时候做了什么时，可以用 m2k 的账本、回执和 `check-delivery`。
结论的可信程度仍取决于验收、可信公钥的取得方式和私钥隔离。

[事后核验演示](../examples/delivery_check/) 不调用真实模型、不需要 API Key，也不联网。
它用本地脚本模型生成签名交付，再展示改文件、删文件、加文件、改回执和无回执目录的核验结果。
演示里的 OBS 私钥就在演示目录中，不能把它当作正式密钥隔离方案。

## 5. 三次实验

### 共同方法与证据范围

判定规则在跑之前写进任务卡，结果出来后不改；打分用工人看不到的隐藏测试作真值。
统计由一个会话做，另一个只读会话用自己的脚本从原始结果重算核对，数字一致才采用。
原始数据与 harness 在仓库外的实验目录，完整记录在各卡的 Review notes。
这里引用的是卡内采用的结果，没有重新跑实验，也没有按新规则改算历史成绩。

### T82：价值对照

[任务卡与 Review notes](../tasks/T82-value-experiment.md)。
问题：同一个可信 Agent 做真实修复任务时，m2k 比所有者跑完自己跑验收多拦下什么？

做法：24 个真实修复任务（普通 12、验收写错的压力题 6、注入 6）。
A 信 Agent，B 跑完自己跑可见验收，C 经 m2k。
Codex（gpt-6-astra）跑全部 24 题 A/C，dsh 跑 6 道注入题 A/C，共 60 次。

事先写死的规则：m2k 比 B 多拦下 ≥ 3 次、确认误报 ≤ 3、额外耗时中位 ≤ +60% 才按原路线；
C 与 B 差 < 3 → 调方向。

结果：坏交付 A/B/C 两个 Agent 都是 0/0/0，多拦下 0 次。
无篡改，6 道注入没有一个被照做；6 道压力题两条线都停下报告矛盾。
成功率 A→C：Codex 18/24→18/24、dsh 6/6→6/6。
额外花费（逐题 C/A 中位）：Codex 时间 2.21 倍、token 1.10 倍，dsh 时间 2.82 倍。
确认误报 3 例，都是审查环节故障。

判定：规则 2，调方向。
dsh 自身的 Windows 沙箱问题削弱了该组证据，具体限制见审阅记录。

### T84：规模化基准

[结果卡与 Review notes](../tasks/T84-r0-scale-benchmark-run.md)，
规则与题库构建见 [T83](../tasks/T83-r0-scale-benchmark-build.md)。
问题：把工作拆给便宜模型，再加可见验收和 AI 审查，能否以更低花费追上贵模型？

做法：从 4 个真实小库挖空 100 个独立函数块，每块有可见与隐藏测试。
① gpt-6-astra 单干；② DeepSeek-V4-Flash 拆分不验证；
③ DeepSeek-V4-Flash + m2k（可见验收 + GLM 审查）。

事先写死的规则：③ ≥ ① 的 90%；③ 花费 ≤ ① 的 40%；
③ ≥ ② + 10 个百分点且坏合并 ≤ ② 的一半。

结果 N=100：按隐藏测试完成 ① 89、② 72、③ 52；坏合并 11 / 28 / 19。
标价花费 ① $2.80、② $1.16、③ $2.79（其中 GLM $1.63）。
N=30：27 / 22 / 15。
GLM 71 次 GO、1 次 NO_GO，且那 1 次可见测试已经挂了。

判定：三条规则全部不过。
原因之一：③ 有 25 块轮数用完未交付，其中 12 块代码已经写对却被丢弃。
这并非唯一原因：审阅记录还指出可见验收导入、临时目录清理的问题及断线补跑不对称。
这些限制随原始结果保留；T85 修正实验 harness 后另做判定，没有替换 T84 的成绩。

### T85：决定性实验

[任务卡与 Review notes](../tasks/T85-r0-decisive-experiment.md)。
问题：把工人看不到的所有者验收作为反馈，并允许退回重做，规模化路线是否成立？

做法：隐藏测试按固定哈希拆成两半——A 给所有者当工人看不到的验收，T 只用来打分。
②\* 自测不过就带失败信息重做；③\* 所有者验收不过就退回重做，各最多 3 次。
① 用 T84 产出按 T 重评，因此不能把两张卡的完成数字直接当作同一评分口径。

事先写死的规则：③\* ≥ ① 的 90%，且 ③\* ≥ ②\* + 10 个百分点。
结果 N=100：① 93、②\* 88、③\* 84。
规则 1 过（84 ≥ 83.7，只多 0.3），规则 2 不过（需 ≥ 98）。
坏合并 ②\* 12、③\* 9；花费 ②\* $1.22、③\* $1.44。

判定：放弃“便宜模型规模化”，m2k 回到审计 / 可核验层。
花费按卡内已知记录引用；断线调用的未知花费和统计限制见审阅记录。

### 合起来看

可信厂商 Agent 单任务，m2k 没多拦下东西；规模化场景，看不到的验收提高了合并精度，
但总完成率不如便宜模型自测重做，更不如贵模型单干（贵模型按标价也不贵）。
这些结果解释了项目为何缩小定位，不能据此宣称 m2k 提高了完成率或能防住攻击。

## 6. 实验暴露、已在 T86 修掉的三处

[T86 任务卡与 Review notes](../tasks/T86-audit-layer-tail.md)。
这些是具体流程缺陷的修复，没有用修复后的代码重跑并改写上述实验结论。

- 预算用完时已写好的候选照常验收和审查，通过就交付；对应 T84 中 12 块写对却被丢弃。
- 审查出错或回复不是单个 JSON 时，用新 nonce 重审一次，原话前 2000 字入账；对应 T82 的 3 次误报及无法诊断。
- 连接层错误按 `retry_delays` 重试，丢失请求的用量记为未知；对应 T84、T85 的断线。

T86 审阅记录另保留了错误响应体读取中断等非阻断遗留，修复范围以该卡为准。

## 7. 项目状态

已封版（2026-10-31）。本卡之后停止开发，不再按原分阶段计划继续扩展。
以下未完成的方向全部冻结：

- 实时等待授权（T81）。
- Windows 账号隔离（T75～T77 之后部分）。
- 记忆与经验库（第 6 阶段）。
- 中断续接（第 4 阶段）。
- 规模化重构（R1～R6）。
- 交给他人（第 8 阶段）。

若将来有真实用户带着上面“没测到的场景”来，再按需要重启。
原来的模块说明和阶段计划保留在 [ARCHITECTURE](ARCHITECTURE.md)，未完成的条目不代表开发承诺。
